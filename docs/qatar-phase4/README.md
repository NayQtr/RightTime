# Qatar MVP — Phase 4 build (staging)

The product is **HerZone** (formerly Rightime): dinners and coffees in Doha **for women only**. The Arabic interface addresses the user in the feminine.

This is the full-stack MVP for the v0.3 spec plus the v0.4 decisions. It includes:

- the database (`app` schema);
- the API (user, admin and payments);
- a mobile-first user web app (AR/RTL and EN/LTR);
- a role-based admin panel.

Everything here is **staging**: OTP codes come back in the API response and payments go through a mock PSP.

## Deployed staging

- **Supabase project:** `qatar-mvp`, ref `fvodcnqmxskgzziwuwmz`, region ap-south-1, Postgres 17.
- **API base:** `https://fvodcnqmxskgzziwuwmz.supabase.co/functions/v1/api`
  - User routes: `…/api/v1/...`, for example `POST …/api/v1/auth/otp:request`.
  - Admin routes: `…/api/admin/v1/...`.
  - PSP webhook: `POST …/api/v1/payments/webhooks/test_psp`, HMAC-signed with `x-signature` and `x-timestamp` (±300 s).
- **Function settings:** the Edge Function `api` runs with `verify_jwt = false` because the API does its own authentication: RS256 user/admin JWTs, plus HMAC for webhooks. It reaches Postgres through the platform-injected `SUPABASE_DB_URL`. No database password or service-role key is in the code or on the client.
- **Web app and admin panel (Vercel):** https://herzone.app (admin: `/admin/`); `www.herzone.app` redirects there (308), and https://qatar-mvp-staging.vercel.app still serves the same build. `WEB_BASE_URL` is `https://herzone.app` and `CORS_ORIGINS` lists it. This is a separate Vercel project, `qatar-mvp-staging`, in team `rightime`, built from branch `rightime-app` with root `qatar/web`. The build copies `config.vercel.js` over `config.js`. The existing projects `rightime` and `rightime-app` were not touched.
- **Region pinning:** the database is in `ap-south-1`, but Edge Functions run next to the caller by default (`us-east-1` from the US), which made each call take about 7–12 s. The web clients therefore add `forceFunctionRegion=ap-south-1` (`apiRegion` in `config.vercel.js`). This is a query parameter, so no extra CORS header is needed. Calls now take about 1.2 s from the US, and should be faster from Qatar.
- **Scheduled jobs (pg_cron, migration 004):**
  - `app_release_expired_holds` runs every minute.
  - `app_refund_unresolved_organizer_cancels` runs every 15 minutes and uses `REBOOK_CHOICE_HOURS`. It creates refunds as `requested`; finance sends them with the batch approval.
- **Data API isolation:** the `app` schema is **not** exposed through the Data API. RLS is on for every table with no policies, and `anon`/`authenticated` have no privileges. Only the server-side function reads or writes data.

## Design system «سُفرة» (spec 2026-10-29)

Spec: `docs/specs/2026-10-29-sufra-visual-redesign.md`. The three direction mockups are in `docs/specs/2026-10-29-design-directions.html`; the owner chose direction A.

- **Colour:** warm paper with Qatar maroon as the one accent, defined in `qatar/design/tokens.json` (light and dark). `python3 qatar/design/contrast_check.py qatar/design/tokens.json` must pass, and `python3 qatar/design/build_tokens_css.py` regenerates `web/tokens.css`. `styles.css` uses tokens only (no hex, no gradients). Elevation is lightness.
- **Type:** Alexandria 700/800 for titles and large numerals, and IBM Plex Sans Arabic 400/500/600 for text, in both languages. Headings are never italic.
- **Text size:** every font size is a multiple of `--u`, the 16px design unit. In browsers `--u` is `1rem` (their text-size setting); on iOS it is the Dynamic Type body size (`-apple-system-body`, 17px by default) scaled back to 16px, so the default looks as designed and text follows the Text Size setting. App chrome (top bar, tab bar, day names, test badge) and the largest headings have a ceiling so bars and long words never overflow; checked at 100/150/200% in Arabic and English. Large English headings are tracked tighter (-0.02em display, -0.01em h1); Arabic is never tracked.
- **Icons:** one family (Lucide) via `icon(name)`. `test/design.test.mjs` fails if an emoji appears in `app.js` or `strings.js`.
- **Table motif:** filled seats only ever show real numbers (`table.confirmed_count` of `table.capacity`); otherwise the seats are dashed.
- **Bottom bars:** the fixed bottom bars are solid and reserve their own space in `main`. The journey test checks that the last content stays above the button.

## User experience (quiz first, spec 2026-10-28)

The user app follows the pattern of the Timeleft screenshots in the `Rightime` Drive folder, with Rightime's own content. Nothing of Timeleft's (name, photos, reviews, numbers) is used.

1. **Welcome**, then the quiz *before* sign-up: 20 questions, one per screen, plus interstitials (Doha, welcome, how it works, research with its source, your card, preparing, ready, safety rules). Answers stay on the device (`localStorage` `q_quiz`) until sign-up.
2. **Sign-up:** first name, phone, OTP, the women-only confirmation («أؤكد أنني امرأة», required), 18+, consents. The answers are then submitted and the device copy is deleted.
3. **What you get:** per-seat fee from the API, benefits, refund rule, FAQ. The page renders a `plan` object so a subscription can be added later.
4. **App:** four tabs. *Home* (Doha, sessions grouped by week), *My events*, *Notifications*, *Account*.

- `GET /api/v1/questionnaires/preview` (no auth) serves the questions to signed-out visitors, with no user data.
- Users who answered an older questionnaire are not blocked. `GET /api/v1/questionnaires/current` returns `has_submitted_any` and `carried` answers (mapped by question and option key), and Home invites them to complete the card.
- Matching (rule `r2-personality`, admin default since 2026-10-30, spec `docs/specs/2026-10-30-personality-matching-design.md`): language, budget, size and blocks are hard rules; every other answer except Q07 is scored, values 32% · personality 28% · social 18% · interests 12% · lifestyle 10% (Q23, Q24 included), with energy (Q12) balanced at each table. After reveal, members see up to three shared themes («يجمعكن: …»), never from age, work, family, children or marital status; a manual move clears them. Migration `011_personality_matching.sql`. `r1-interest` stays selectable.
- Copy rule (owner-approved, 2026-10-31): "what you get" and the FAQ say «نجمعكِ مع من يشبهنكِ في القيم والشخصية والاهتمامات، بلغتك وضمن ميزانيتك.» / "We seat you with women who share your values, personality and interests, in your language and within your budget." All 20 questions stay before sign-up (owner decision); the welcome says they are short and take a few minutes.

## Admin sign-in (TOTP)

Admins have no passwords. Each one enrols once with a single-use token (valid 24 h), then signs in with email plus a 6-digit TOTP code.

- **Issuing a token:** an owner calls `POST /api/admin/v1/admins/{id}:enroll-token`.
- **The very first owner:** issue the token with SQL in the Supabase SQL editor, using any random string as the token:

  ```sql
  UPDATE app.admin_users
     SET enroll_token_hash = encode(sha256(convert_to('<token>', 'UTF8')), 'hex'),
         enroll_expires_at = now() + interval '24 hours'
   WHERE email = '<owner email>';
  ```

- **Enrolling:** open `/admin/#/enroll`, enter the email and token, and add the shown secret to an authenticator app.

The seeded admins use `@example.test` addresses and are placeholders. Replace them with real staff before use.

| Key | Staging | Production |
|---|---|---|

| `MOCK_PSP_ENABLED` | `true`: `/checkout/mock/{booking_id}` and `/api/mock-psp/*` | **`false`**; needs a real PSP adapter (O05) |
| `WEB_BASE_URL` | `https://qatar-mvp-staging.vercel.app` (`http://localhost:8787` for local runs) | the hosted web app origin |
| `CORS_ORIGINS` | `https://qatar-mvp-staging.vercel.app,https://qatar-mvp-staging-rightime.vercel.app` | the web app origin(s) only |
| `SEAT_HOLD_MINUTES` / `REBOOK_CHOICE_HOURS` / `FEEDBACK_WINDOW_DAYS` | 10 / 48 / 7 | per policy |
| `PACKING_MODE` | `min_leftovers` (`greedy_6` also available) | per v0.4 decision |

**Server keys (audit F6).** The five keys (`JWT_PRIVATE_PEM`, `DATA_KEY`, `PHONE_PEPPER`, `PSP_WEBHOOK_SECRET`, `SEAT_TOKEN_KEY`) can each be set as an Edge Function secret. A key that is not set is generated once and kept in `app.server_keys`.
- With the Edge Function secret `SERVER_KEYS_KEK` set (any random text of 40+ characters, entered only in the Supabase dashboard), every row in `app.server_keys` is stored encrypted (AES-256-GCM, `enc:v1:` prefix). Existing plaintext rows are encrypted in place on first use, keeping their values, so encrypted phone numbers and admin TOTP secrets stay readable.
- A missing or wrong KEK fails closed (HTTP 500). The keys are never regenerated over existing data.
- `GET /api/v1/health` reports `key_source`: `env`, `db-encrypted`, `db-fallback` (plaintext) or `mixed`.
- Never change or delete `SERVER_KEYS_KEK` once rows are encrypted. Without it the keys cannot be decrypted.

### Auto-save and finishing later

Nobody has to start again from zero.

| Moment | Where progress is kept | How the user continues |
|---|---|---|
| Quiz, name, phone, before sign-up | This device only (`localStorage`: `q_quiz` answers, `q_resume` last step, `q_quizName`, `q_phone`) | Welcome shows "Continue where you left off" with the saved answer count; "Start over" clears it |
| Code screen | The pending challenge in `sessionStorage` until it expires | A reload stays on the code screen |
| Signed in, editing answers | Server draft (`POST /questionnaire-responses`, `status: draft`), debounced and flushed when the tab is hidden | Any device, after signing in with the same number; the quiz opens at the first unanswered question |
| Booking held, not paid | Server (`payment_pending` booking) | Home shows it with a link back to payment |

- The device copy is deleted when the answers are submitted, on "Start over" and on sign-out.
- No IP address, device fingerprint or tracking cookie is used to recognise a person or restore data. A shared or carrier IP (common on mobile networks) would show one person's answers to another.
- Every API call is retried once on a dropped connection, and reads once more on a 502/503/504. The retry reuses the Idempotency-Key, so a write is never applied twice.

### Women only (HerZone)

- Self-declaration: `POST /api/v1/users/me/registration` requires `woman_confirmed: true` (else 422 `WOMEN_ONLY`) and stores `users.woman_confirmed_at`. There is no gender question (Q10 was removed in QA-2026-03). A false declaration is handled as a conduct case (report, ban).
- Accounts registered before the change have `woman_confirmed: false` in `GET /api/v1/users/me`; Home shows a banner, and `POST /api/v1/users/me/consents` with `{ "consents": [], "woman_confirmed": true }` records it. `POST /api/v1/bookings` returns 422 `WOMEN_ONLY` until then.
- The server-key derivation label `rightime/server-keys/v1` in `keys.js` keeps the old name on purpose: changing it would make the stored keys unreadable.

### Contact requests after the meetup

- From the meetup's end and for 7 days, the meetup details show «التواصل بعد اللقاء»: each tablemate's first name with «طلب تواصل».
- `GET /api/v1/bookings/{id}/contacts` lists tablemates by opaque seat with a state: `none`, `sent`, `incoming` (with `request_id`), `connected` (with `whatsapp_url`).
- `POST /api/v1/contact-requests { booking_id, seat }` sends one (notification `CONTACT_REQUEST`). If she had already asked the sender, both are connected at once.
- `POST /api/v1/contact-requests/{id}:accept | :decline`. Accepting notifies the sender (`CONTACT_ACCEPTED`) and gives each a `https://wa.me/…` link to the other; the number is never printed in the app.
- A refusal, no answer, a block or a suspended account is never revealed: the sender only ever sees «أُرسل الطلب». A request to or from a blocked pair is stored undelivered, and a later block hides an existing link.
- The window follows the session's actual end time. The old silent «أرغب بالتواصل» picker in the rating form was removed (`connection_consents` is kept for history).

### Privacy notice updates

- `GET /api/v1/users/me` returns `outdated_consents`: required consents whose latest grant is for an older document version.
- `POST /api/v1/users/me/consents` records acceptance of the current version (idempotent; refusing a required consent returns `CONSENT_REQUIRED`, since that is done by deleting the account).
- Home shows the update with the full text and an "I've read it and agree" button; Account links to the current notice (`#/privacy`).
